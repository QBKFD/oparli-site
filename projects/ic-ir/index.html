IC/IR Alpha-mining Engine

An alpha-mining engine built data-first: a survivorship-free S&P 500 universe, honest cross-sectional scoring, then a ranking kernel I made about 1.9 times faster.

Polars · NumPy · Point-in-time universe · Planted-signal validation · Thread-pinned benchmarks  ·  Repo →

  1. 01 · Idea

    Start from the engine, not the asset

    I started by researching how alpha-mining engines are actually built, and whether one engine could generalise across assets instead of being hand-tuned to a single market. The conclusion that shaped everything after it was simple: an engine is only as honest as the data you feed it, so the data had to come first.

  2. 02 · Survivorship bias

    The first place a backtest cheats is the universe

    Before any signal, I looked at what data I was even allowed to use. Most equity datasets quietly contain only the companies that survived. Test on those and every strategy looks better than it really was, because the failures have been deleted. To trust anything downstream, I needed a universe that still remembers the companies that left.

    This is the dataset most people use: only the survivors. The backtest looks great, and that is exactly the problem.

  3. 03 · Reconstructing the universe

    Rebuild membership by walking the change log backward

    I took today's S&P 500 as ground truth and walked the full membership change log backward, undoing each addition and removal to reconstruct who was actually in the index at every month-end. That means fetching the delisted and removed names too, not just the survivors. The result is point-in-time and deterministic, covered by 12 unit tests, and I only score from 2007 onward, where the change log gets dense enough to trust.

  4. 04 · Scoring

    Rank IC, IR, and decay in one lazy pass

    On that universe, the engine scores each candidate signal by cross-sectional Spearman rank IC, information ratio, and decay, all in a single Polars lazy pass rather than a Python loop per factor. I validate the scorer itself against planted signals first, so I know the metrics track real structure and not my own hope.

  5. 05 · Making it fast

    Rank once per date, not once per factor

    Spearman rank IC is just Pearson correlation on ranks, and the ranking is a sort that turns out to be almost the entire cost: about 989 ms of a pass where the correlation itself is only 18 ms. The baseline, Polars' built-in per-factor Spearman, re-ranks the returns again for every factor, so a thousand factors means sorting the same returns a thousand redundant times.

    Instead I rank each column once per date, the returns once and each factor once, then score with a cheap Pearson on the ranks I already have. Against that baseline it is about 1.9 times faster over a thousand factors, 23.4 down to 12.1 seconds single-threaded, and it holds on 8 cores too. It is exact only when every factor shares the same valid rows, so the null-aware version is what I am building next.
