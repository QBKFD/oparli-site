Project

Self-Evolving Multi-Agentic AI Trading System

A multi-agent system that trades spot gold, runs the exact same code live and in backtest, gates its expensive AI behind a cheap filter, and proposes evidence-backed changes to its own agents that I have to approve.

Python · FastAPI · Claude Vision + Text · IBKR · PostgreSQL · Vue 3  ·  Repo →

  1. 01 · The bet

    Separate deciding from analysing

    The core rule of the system is that no single agent both analyses the market and pulls the trigger. Each analyst only offers an opinion. A meta-agent weighs those opinions into a decision, a risk manager validates it, an execution agent places it, and a position manager owns its life after that. Splitting the roles keeps every step auditable and stops one overconfident model from running the whole show.

  2. 02 · The pipeline

    Specialists in, one weighted vote out

    A scanner watches XAUUSD and, when something interesting happens, fans the moment out to three analysts: a rule-based technical agent (RSI, MACD, Bollinger Bands, moving averages), a visual agent that reads a rendered chart image with a vision model, and a sentiment agent for macro context. The meta-agent tallies their signals as a weighted, governed vote, resolves conflicts against consensus and confidence thresholds, and only then emits a trade signal to the risk manager.

  3. 03 · Cost-aware AI

    Keep the expensive thinking rare

    Vision and language-model calls cost real money, so the scanner filters in two stages. Stage one is pure Python and runs in under 100 milliseconds: it rejects anything that is not at a key level, on a volume event, or above a confluence floor. Only when stage one passes does stage two wake the visual, sentiment, and meta agents at full LLM cost. The cheap gate reacts to genuine structure while keeping the costly path infrequent.

  4. 04 · One codebase, two modes

    The same agents trade live and replay the past

    The hard part of a trading system is trusting that a backtest reflects what will actually happen. I handle it by never letting agents read the wall clock or the live database directly. They receive an injected clock and data provider, so a live clock and Postgres in production become a simulated clock and a bounded historical feed in a backtest. The historical provider is pinned to an as-of timestamp and binary-searches its frame, which makes look-ahead impossible by construction. The backtest harness just swaps those two objects and replays the exact same agent code.

  5. 05 · Self-evolving, with a veto

    Two layers of learning, and a human in the loop

    The meta-agent runs in four modes. Before a trade it coordinates the vote, mid-trade it manages the position, after a trade it nudges each analyst's weight up or down from realised performance, and once a month it does something bigger: it reads a breakdown of where an agent has been failing and proposes a change to that agent's own instructions, add, modify, or remove. Nothing deploys automatically. Every proposal waits for my approval.

    The hard part is not proposing changes, it is knowing when one is even warranted. A run of losses can mean an agent's reasoning is genuinely broken, or that the market regime turned, or nothing beyond variance. Today the system guards against overreacting with a minimum-sample floor before evolution can trigger, and by splitting performance per market regime so a regime shift is not mistaken for a broken agent. Where it is going is stricter: a significance gate that tests the recent window against a bootstrapped no-change baseline, and canary cases the agent must keep getting right, so a proposal only survives if the degradation is real and the fix does not break what already worked.
